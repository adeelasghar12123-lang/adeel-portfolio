Measuring LLM Serving Performance Under Load

9 min read

Before reading: for a general introduction to the serving pipeline, start with a short explanation of prefill, decode, continuous batching, and request scheduling.

An online model server looks simple from the outside: receive a request, run the model, return generated tokens. Under load, however, several different measurements start to matter. A system may have acceptable average latency while still producing slow tail requests, or it may achieve strong throughput while making the first token feel unacceptably slow.

This study focuses on three questions:

  • How do first-token and decode latency change as request pressure grows?
  • How does throughput behave before the server becomes saturated?
  • Which scheduling settings change capacity and tail latency most clearly?

The goal is not a single score. It is to separate the pieces of serving performance so the bottleneck is easier to understand.

Why this matters

New model requests arrive independently while the server shares the same GPU across them. Prefill, decode, batching, memory movement, and scheduling all compete for the same compute budget.

A useful serving benchmark therefore reports first-token latency, decode latency, throughput, concurrency, and some measure of tail behavior. Average request time alone can hide an overloaded period.

What we did

I measured a small instruction-tuned model on a single GPU and varied the request pattern rather than relying on one isolated benchmark. The tests included light traffic, burstier traffic, and longer sustained runs.

  • Separated time-to-first-token from subsequent token generation.
  • Measured throughput under increasing concurrency.
  • Looked at queueing behavior during bursts.
  • Compared scheduling settings that changed the amount of work admitted to each iteration.

The important design choice was to preserve the request-level view. A high aggregate tokens/sec number is useful, but it does not tell us whether individual requests are waiting behind a large batch.

Poisson traffic: first-token latency falls first

Under a steady random arrival process, the first visible effect of growing request pressure was queueing before the first generated token. Decode behavior remained comparatively stable for a while, then worsened as the GPU approached saturation.

These results match a useful mental model: when a new request arrives, it may first wait for the server to admit its work. The total request time can therefore rise even before the per-token decode kernel changes much.

Fixed bursts: how average request rate hid an overloaded moment

Short bursts produced a different shape. A low average arrival rate could still contain a moment where many requests were admitted together. During that period, queueing and scheduling made some requests much slower than the average suggested.

Effect of scheduling settings on latency and capacity

Scheduling settings control how much work is admitted in each iteration. A larger batch can improve GPU utilization, but it can also delay individual requests if the batch waits for more work or contains requests with different remaining lengths.

The right setting is therefore workload-dependent. The measurement should include both aggregate throughput and per-request latency, especially the tail.

ConfigurationQueue behaviorThroughputLatency trade-off
Small admission windowSmaller queuesLower peakMore responsive
Moderate windowBalancedHigherBalanced
Large windowMore batchingHigher until saturationTail can increase

Conclusion

First-token latency is often the first place serving pressure becomes visible. A server can maintain reasonable decode throughput while requests spend more time waiting to begin. Bursty traffic makes the problem harder because a good average arrival rate can still contain an overloaded moment.

The practical benchmark is therefore multi-dimensional: report TTFT, decode latency, throughput, concurrency, and tail behavior together. The exact numbers depend on the GPU, model, runtime, prompt distribution, and scheduling policy used in the experiment.
