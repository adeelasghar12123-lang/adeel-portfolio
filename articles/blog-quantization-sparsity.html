Do Quantization and Sparsity make LLM Inference Faster?

12 min read

Before reading: this article assumes a basic understanding of Transformer inference, including attention, Q/K/V projections, model weights, and decode. If those concepts are unfamiliar, start with a short Transformer overview first.

Quantization and sparsity are attractive because they appear to reduce the amount of work an inference system has to do. Quantization stores weights using fewer bits; sparsity removes or skips selected values. In both cases, the model representation becomes smaller.

That does not automatically mean the end-to-end system becomes faster. The result depends on the kernel, the matrix shape, memory traffic, batch size, and whether the hardware can actually exploit the compressed representation.

The question for this experiment was simple: when does a smaller representation turn into measurable inference improvement, and when does it only change the model's memory footprint?

Why this matters

Lower precision can reduce memory movement and may unlock specialized hardware paths. Sparsity can reduce arithmetic work when the execution stack knows how to skip the values efficiently. But if the runtime has to unpack values, convert layouts, or execute an unsupported kernel, part of the theoretical gain can disappear.

For practical engineering, the useful metric is therefore not compression ratio by itself. It is the latency, throughput, and resource use of the complete serving path.

What we did

I compared several representations of the same model and looked at the metrics that matter for inference rather than only looking at model size.

  • Compared higher-precision and lower-precision weight representations.
  • Looked at memory traffic and execution time separately.
  • Considered different workload sizes instead of relying on a single batch.
  • Checked sparse and dense execution paths as separate cases.
  • Focused on end-to-end inference behavior, not only an isolated kernel.

Does FP16 give the best baseline?

A higher-precision representation is a useful baseline because it tells us what the uncompressed execution path looks like. It also makes it easier to separate two different effects: less memory traffic and less actual execution time.

RepresentationWeight sizePotential benefit
FP16BaselineWide kernel support and predictable execution
INT8SmallerLower weight traffic when an efficient integer path is available
INT4Much smallerStrong memory reduction, but more dependence on supported kernels

INT8: fewer bytes do not automatically mean fewer milliseconds

INT8 can reduce the number of bytes moved from memory. That can matter when decode is limited by memory bandwidth. But the runtime may also need additional conversion, packing, or specialized kernels, so the observed speedup can be smaller than the reduction in weight size.

This is why the experiment measures both memory-related effects and wall-clock latency. A memory optimization is valuable, but the user experiences the full request path.

INT4: the representation gets smaller, the implementation matters more

Moving from 8-bit to 4-bit weights increases the opportunity to reduce memory traffic even further. The trade-off is that the runtime has less room to hide implementation overhead. Efficient fused kernels and compatible hardware can turn the smaller representation into a useful speedup; otherwise, some of the benefit remains theoretical.

QuestionWhat to measure
Did memory use fall?Peak and steady-state GPU memory
Did decode get faster?Per-token decode latency
Did throughput improve?Tokens/sec across multiple batch sizes
Did the implementation add overhead?Kernel time and conversion time

Why 2:4 sparsity is easier to use than arbitrary sparsity

Unstructured sparsity can produce many zeros without imposing a regular layout, but irregular access can make those zeros difficult to exploit efficiently. Structured sparsity gives the hardware and kernels a predictable pattern, which makes the reduction in work easier to schedule.

The practical lesson is that sparsity needs a matching execution strategy. A sparse model is not automatically a sparse computation.

Measure the end-to-end system, not just the model

For serving workloads, the right experiment separates prefill and decode, reports throughput at more than one batch size, and measures latency at the request level. It is also useful to record peak memory and the variance between repeated runs.

# The important measurement is the complete request path.
start = perf_counter()
output = engine.generate(prompt, max_new_tokens=128)
elapsed = perf_counter() - start

latency_per_token = elapsed / len(output.tokens)
tokens_per_second = len(output.tokens) / elapsed

Conclusion

Quantization and sparsity change the amount and structure of computation, but neither one guarantees faster LLM inference by itself. The result depends on the interaction between the model representation, the kernels, the hardware, and the workload.

The most useful benchmark therefore reports the actual serving behavior: latency, throughput, memory, and the conditions under which each optimization was measured. Compression is an input to the optimization problem; end-to-end performance is the result.
