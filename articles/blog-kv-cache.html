How much KV cache can you prune before quality degrades?

10 min read

Before reading: if the KV cache is unfamiliar, read a short explanation of caching. It explains why an LLM stores keys and values from earlier tokens instead of recalculating them for every new token.

During inference, an LLM first processes the prompt and then enters decode, where it generates one new token at a time. For every decoded token, the attention layers have already calculated key and value vectors for earlier tokens. The KV cache stores those vectors so the model can reuse them instead of calculating the complete history again for every new token. Each decoded token adds another set of key and value entries to the cache.

This makes the cache grow with context. Longer caches require more GPU memory, and each new decode step must read those stored vectors. On memory-constrained GPUs the KV cache can therefore become a practical limit on context length even when the model weights themselves fit in memory.

One possible solution is to remove old cache entries that appear less useful. That saves memory and attention work, but removing the wrong tokens can make the model worse at predicting what comes next. The question was: how much KV cache can we remove before quality meaningfully degrades, and how much memory and speed do we recover?

Why this matters

Long contexts can exhaust GPU memory even when the model itself fits. They can also make every new token slower. A useful pruning policy has to balance three outcomes: prediction quality, live KV memory, and decode speed.

What we did

I tested a small causal language model on one GPU and implemented two policies using a Hugging Face-style cache interface.

  • Sinks plus recent window: keep the first few tokens and use the rest of the budget for the newest tokens. The first tokens are retained because they can act as attention sinks, meaning later tokens may continue attending to them even when they are not recent.
  • Attention score plus recent tokens: keep a small set of early tokens, always keep the newest window, and fill the remaining space with older tokens that received the most attention. The policy assumes past attention may help identify future usefulness.

For quality, I warmed up the model on a fixed token prefix, then measured perplexity over the following predictions. Lower perplexity is better because it means the model is less uncertain about the correct next token.

Recent windows: one-third less cache, nearly unchanged quality

A recent-window budget produced almost the same perplexity as the full cache until the retained-token budget became noticeably smaller. The first measurable quality cost appeared once the retained region was reduced far enough to remove more of the long-range context.

Attention scores did not improve perplexity

The attention-score policy kept older tokens that had received more attention in the past. This sounds reasonable, but past attention did not predict future usefulness better than recency on this continuous-text stream.

This does not show that attention-guided pruning is universally wrong. A prompt that repeatedly references an important early token could benefit from retaining it. The result here is narrower: for this workload, the simple recency policy was a stronger signal than the single attention heuristic we tested.

Bounded windows: memory and decode-time impact

The full cache grew with every decoded token because each layer stored key and value vectors for that token. Once a bounded window reached its budget, live memory stopped growing because each new entry replaced an old one. The model also avoided reading the complete history at every attention step, so decode time became more stable.

Pruning also has a small implementation cost when selecting and copying cache entries into a new layout. On long contexts, the saved attention work can outweigh that overhead; on short contexts, the extra bookkeeping can become a larger fraction of the runtime.

Conclusion

KV-cache pruning had a useful middle region in this experiment. A recent window removed a substantial part of the cache while preserving quality relatively well. Smaller budgets saved more memory and could stabilize decode work, but perplexity worsened more quickly.

The practical choice depends on whether quality, maximum context, or decode speed matters most. The workload here is one continuous test stream, so the results should not be treated as a universal cache policy. A production implementation should measure the quality of its own traffic and account for the overhead of selecting, copying, and managing cache blocks.
